# Paperless inbox suggestions: fresh E2E result

In a fresh 18-slot browser run, the complete requirement (A) and its meaning-preserving rewrite (B) each passed **6/6**. When the automatic-on-open sentence was omitted (C), **4/6** implementations failed that obligation while **2/6** implemented it despite the omission. All 18 generated HTMLs were valid and evaluable; none failed on the surrounding page checks. Luna produced one C target failure and two C passes; Sol produced three C target failures. This is a local effect for **one requirement in Paperless-ngx**, not a general H1 estimate. It does not test H2.

The public usage guide says suggestions are automatically requested when an inbox-tagged document opens. The [prospective contract](2026-10-01-paperless-inbox-suggestions-e2e-contract.md) and [admission record](2026-10-01-paperless-inbox-suggestions-admission.md) define the source, A/B/C contrast and browser boundary. The fixed, offline page exposed two different inbox documents and a suggestion-returning API. Without clicking Suggest, the browser checked that each page called the API exactly once for its own document and showed the returned label. Title, document ID, button, suggestion area and console checks kept unrelated breakage out of the target-failure category. This measures the request trigger and visible suggestion, not suggestion quality or acceptance.

The v3 schedule was frozen before these generations: two model configurations, three repetitions per arm, randomized order, no retries, and a qualified browser oracle. Its exact instrument passed **14/14** authored browser controls and **3/3** pre-generation no-material-blocker reviews. Eighteen calls yielded 18 distinct HTML hashes and 18 completed browser reports. The private packet's **283/283** file hashes verified after finalization. Earlier attempts remain separate in the [collection history](../../data/e2e-paperless-inbox-suggestions/replication-20261001-v3/history.json). In v1, a false-positive oracle treated labels decorated with Accept/Reject buttons as missing: 17 valid outputs were originally classified as failures, including correct A/B behavior; one output was invalid. A later browser-only diagnostic of the **same** HTMLs gave A 5 passes plus one invalid, B 6 passes, C 6 target failures. That diagnosis does not overwrite the frozen v1 result. After repairing and requalifying the oracle, v2 stopped at a provider-capacity error: eight browser-evaluable outputs (B 4 passes, C 4 target failures), one provider error, nine slots not attempted and no A observations. V3 is a new generation schedule, not a backfill of either run.

The v3 result supports a bounded claim: four pages generated under the omission condition lacked the explicit trigger, while two C pages implemented it despite the omission. The two C successes do not identify a contextual recovery mechanism: scaffold cues, prior knowledge and other explanations were not isolated. Repetitions are nested within this one requirement; they cannot stand in for independent requirements or projects. The oracle repair was informed by v1 generated output, so this whole sequence is exploratory. A broader H1 analysis still needs independently reviewed mappings and labels across requirements and projects, with the requirement as the analysis unit and uncertainty reported. H2 needs its separate provenance comparison.
