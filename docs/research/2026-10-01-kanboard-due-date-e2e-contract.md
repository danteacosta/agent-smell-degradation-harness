# Kanboard due-date colors: prospective browser contract

The pinned Kanboard `tasks.md` says overdue due dates are red and upcoming due dates are black **on the board**. Its Due Date bullet also requires several accepted input formats and a picker. This candidate tests **only the red/black rendering subclause** in a bounded generated board. It cannot establish compliance with the complete bullet, input formats, or picker. A and B retain both color conditions; C removes that color rule while retaining the other words. Its source and license hashes are in the [six-case selection](2026-10-01-prospective-six-selection.md). The first exact-instrument panel identified a scope ambiguity; the second identified parent-versus-child text color measurement and missing date classification semantics. Those votes remain in custody. The current instrument addresses both and requires fresh admission before any generation.

ATDD acceptance: given the same fixed HTML shell and neutral `window.boardTasks` API for A, B and C, when a model implements the visible board in separate contexts, the browser identifies one overdue and one upcoming task under a private UTC clock and observes the **foreground color of the visible due-date text**. Overdue red and upcoming black must be checked separately, using two fixtures with different task IDs and dates strictly before/after the clock. Task IDs, titles and due-date text are non-target controls. The common prompt says to show each due date in ISO form so C still has a date to color; it never states the missing color mapping. The scaffold implements neither color. A user can see the cards and their date colors in the screenshots.

BDD scenarios:

- Given two correct implementations with different code structures, when the browser opens each fixture, then both due-date colors and all neutral content pass.
- Given an overdue date rendered in black, an upcoming date rendered in red, or color applied only to the card background, when the browser reads the **date text** foreground, then only the target fails.
- Given a wrong title or due-date text with correct colors, when the browser inspects the board, then only a non-target control fails.
- Given duplicate task IDs, missing/hidden/covered date text, malformed color or browser error, when classification runs, then no target success or defect is inferred.
- Given A/B/C generated HTML, when a model changes the fixed shell or fails to insert behavior, then the output is invalid before browser scoring.

The browser uses fixed dates away from the due-today boundary. The common prompt defines overdue/upcoming relative to the current UTC day without stating colors. The runner checks computed foreground color for every visible due-date **text node**, including nested spans, so a parent style cannot mask a child override. It accepts a red category (computed RGB: R ≥ 100, R ≥ 1.5×G and R ≥ 1.5×B, G/B ≤ 160) and a near-black category (all RGB channels ≤ 70), not an exact Kanboard palette. These thresholds, selectors, controls and runtime must be qualified and frozen before generation. The implementation belongs to a small page scaffold, runner, fail-closed classifier and authored-control qualifier. No new abstraction is needed; the provider collector can follow the existing one-attempt, private-custody pattern. The risks are CSS colors that are technically in range but perceptually different, inaccessible reliance on color alone in the source, and contextual recovery of the mapping by C. Report all unknowns and ties. Browser color outcomes are not independent ordinal H1 labels; H2 remains separate.
