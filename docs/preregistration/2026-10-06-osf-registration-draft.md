## Study information

**Title.** Recoverability of omitted requirement rules in code generated by large language models: confirmatory collection.

**Authors.** Dante Costa (PPGI/UFAL); [DECIDE: advisor name and order].

**Description.** Coding models implement user-interface requirements taken from the documentation of open-source web applications. For each requirement, a browser oracle checks one target rule. The model receives one of three texts:
- the complete requirement (A);
- a meaning-preserving rewrite of it (B);
- the requirement with exactly the target rule removed (C).

The study asks how often the omission makes the generated page violate the rule, and which properties of the rule predict that the model recovers it anyway. An exploratory collection of 46 requirements in 9 projects, run before this registration, is not part of this sample.

**Hypotheses.**
- **H1a.** For the same requirement, C violates the target rule more often than A. [DECIDE (decision 5): one-sided, or two-sided with a reversal reported as such. The frozen analysis reports both; the registration fixes which counts as the claim.]
- **H1b.** In arm C, violation is less likely when the rule is inferable from other context (`context_cue`), and more likely when the rule is numeric (`numeric`) or changes the state of another entity (`derived_state`); `memorized` enters as a control. H1b is estimated, not powered for small effects. [DECIDE (decision 6): whether `conditional_rule` replaces a covariate or stays exploratory.]
- **H2.** [DECIDE (decision 3): kept here, or moved to future work.]

## Design plan

**Study type.** Experiment, with a within-requirement manipulation of the requirement text.

**Blinding.**
- Oracle authors and manipulation reviewers do not see generated outputs.
- Generation never sees oracles or labels.
- Covariate coders do not see outcomes.

**Design.**
- Arms A, B and C for each requirement.
- [DECIDE (decision 4): coding models. The two pinned models of the exploratory collection, plus a model from another provider if affordable (cost note from the Codex feasibility PR).]
- Two repetitions per model and arm.
- Exact dated model identifiers are listed in the frozen receipt. No arm mixes identifiers.

**Randomization.** A seeded shuffle of all (requirement, arm, model, repetition) slots, frozen before the first call.

## Sampling plan

**Existing data.** The following are excluded from the confirmatory sample and reported as exploratory:
- the 46-case collection;
- the pilot cases;
- the historical arm;
- the two mutation-adequacy studies.

A candidate that overlaps an exploratory requirement is excluded with reason `overlaps_exploratory`.

**Data collection procedures.**
- **Frame.** Two mechanically mined frames with the registered filters:
  - **reserve:** registered window 2025-01-01 to 2026-09-30, candidates never screened;
  - **w2024:** 2024-01-01 to 2024-12-31.
- **Screening.** Both frames were screened by the blind LLM panel on 2026-10-05, with 95 and 67 provisional admissions respectively. A human audit of a stratified random 20% of the panel's decisions (#176) is completed before selection: [DECIDE/ATTACH: audit result].
- **Selection (#177).** Per project, reserve candidates come first in seeded order (seed 2026100506), and 2024 candidates only complete a project.
  - Each examined candidate is either qualified (mapping reviewed, oracle qualified) or excluded with one of six reasons: `duplicate_semantic`, `overlaps_exploratory`, `mapping_invalid`, `not_constructible`, `oracle_not_qualified`, `human_audit_exclude`.
  - Every decision is appended to the ledger with date, decider and evidence.
- **Memorization probe.** Run before generation and coded as `memorized`.

**Sample size.** 8 projects × 5 requirements = 40 requirements. With two models: 480 generation calls; [DECIDE: ×1.5 with a third model].

**Sample size rationale.** The project-level simulation (`confirmatory_power.py`, v2) gives the following power for an effect near 0.60:

| Noise | Power |
| --- | ---: |
| Pair noise 0.047 | 0.960 |
| Stress noise 0.14 | 0.835 |

Power is computed for the conjunction of the exact project sign flip and the project-bootstrap bound.

The minimum expected use of the 2024 window is 3 of 40 requirements. Later exclusions may need more.

**Stopping rule.**
- Selection stops when every project has 5 qualified requirements. If any project exhausts its ordered list below 5, the procedure stops with `stopped_insufficient`, and any remedy is a new, recorded decision.
- Collection stops when every frozen slot has been attempted once. There is no retry, repair or regeneration.

## Variables

**Manipulated variables.** The arm: A, B or C.

**Measured variables.**
- **Primary:** the frozen browser oracle verdict for the target rule (pass, fail or unknown).
- **Secondary:** whether generated acceptance criteria contain the rule. [DECIDE (decision 1): keep the browser oracle as primary.]

**Indices / covariates.**
- **Coded before generation, blind to outcomes:** `context_cue`, `numeric`, `derived_state`, `memorized`.
- **Recorded, exploratory only:** `conditional_rule`, `domain_convention` and the frame window.

## Analysis plan

**Statistical models.** `scripts/confirmatory_analysis.py`, frozen and tested on synthetic data before registration:
- **H1a:** paired probability of superiority of C against A. A pair scores 1 if C is worse, 0.5 on a tie, 0 if C is better. Repetitions are averaged within the requirement, with equal weight per requirement.
- **B control:** the same estimand for B against A.
- **H1b:** mixed-effects logistic regression of the C-failure indicator on the four covariates, with random intercepts for project and requirement (`scripts/h1b_agq.py`). Reports odds ratios with 95% profile intervals.

**Inference criteria.**
- **H1a supported:** the 95% project-cluster bootstrap interval (4,000 resamples) lies above 0.5, **and** the exact two-sided sign-flip test at the project level (all 2^8 assignments) gives p < 0.05.
- [DECIDE (decision 5): whether "reversal" (upper bound below 0.5 and p < 0.05) is a registered outcome.]
- The requirement-level sign-flip test is not used for inference, because requirements within a project are not exchangeable.
- **B wording effect:** flagged if the B interval excludes 0.5. It limits the interpretation of C.
- No multiplicity correction for the four pre-specified H1b terms.

**Data exclusion.** An output that is not valid HTML or changes the frozen scaffold is recorded as invalid and treated as unknown.

**Missing data.**
- Unknown outcomes are reported per arm.
- The primary estimate uses observed pairs.
- Worst-case and best-case assignments are reported as bounds.

**Exploratory analysis.**
- Per model and leave one project out.
- Per frame window, plus the sensitivity without 2024, which does not keep the design or its power.
- `conditional_rule` and `domain_convention`.
- Acceptance-criteria coverage.
